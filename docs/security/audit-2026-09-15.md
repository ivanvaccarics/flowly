# Security audit — Server MVP, 2026-09-15

Scope: the self-hosted server, the browser client, the Compose deployment and the
Enable Banking connector, at the tip of `main` after the raw-record and
callback work. This is a self-audit by the maintainer's tooling, not an
independent review: the cryptographic design still awaits one (see
`docs/PLAN.md`).

## How this was checked

- Read the security-relevant paths: `crypto/`, `vault/vault.ts`,
  `storage/sqlcipher-driver.ts`, `session/session-store.ts`, `api/app.ts`,
  `api/banking-routes.ts`, `portability/`, `banking/`, the Compose stack and the
  Caddyfile.
- `pnpm verify` (177 server, 36 web, 10 contract tests), `pnpm build`,
  `pnpm release:check` (license policy) and `pnpm release:report` (SBOM and
  inventory, committed).
- `pnpm audit --prod` → **no known vulnerabilities** in production
  dependencies.
- Pattern scans over `apps/` and `packages/`: `dangerouslySetInnerHTML`,
  `innerHTML`, `eval`, `new Function`, `child_process`, `Math.random` → none.
- Repository hygiene: `git grep` for provider identifiers in tracked files →
  only synthetic `TEST_*` values; `.dockerignore` covers `.env`, `secrets`,
  `data`, `.git`; `git ls-files` shows no secret file is tracked.
- Network position: `lsof` shows the published port bound by Docker; `upnpc -l`
  read the router's UPnP table (no mapping points at this host).

## Findings

| # | Severity | Area | Status |
| --- | --- | --- | --- |
| A1 | Medium | Proxy trust: `trustProxy: true` accepted a client-written `X-Forwarded-For` | **Fixed** |
| A2 | Low | API responses had no `Cache-Control`, so financial JSON was cacheable | **Fixed** |
| A3 | Low | CSP had no `form-action` directive | **Fixed** |
| A4 | Low | Argon2id parameters sit exactly on the OWASP minimum | Recommendation |
| A5 | Low | Raising KDF parameters never reaches an existing vault | Recommendation |
| A6 | Low | SQLCipher arrives through a community binding | Accepted, documented |
| A7 | Info | The plain-text tables ZIP carries provider payloads and ids | By design |
| A8 | Info | The bank callback is unauthenticated and unrated-limited | By design |
| A9 | Info | `FLOWLY_BIND_IP=0.0.0.0` publishes on the LAN and the tailnet | Operator choice |
| A10 | Info | A plaintext `.pem` copy of the Enable Banking key sits in `secrets/` | Operator action |

### A1 — Forged `X-Forwarded-For` (fixed)

The server ran Fastify with `trustProxy: config.trustProxy`, i.e. `true` behind
the bundled proxy, so `request.ip` was taken from the **leftmost**
`X-Forwarded-For` entry — the one a client writes. Caddy appends the address it
really saw, so a caller could send `X-Forwarded-For: 1.2.3.<n>` and get a fresh
bucket per request in two places that matter:

- the unlock rate limiter, turning five attempts per minute per address into
  unlimited attempts;
- the PSU address forwarded to Enable Banking, because `psuFrom` reads
  `request.ip`.

Fixed by trusting only the ranges the proxy can come from
(`loopback`, `linklocal`, `uniquelocal`): proxy-addr then walks the chain from
the socket and stops at the first address the client cannot forge. Covered by a
test that sends four unlock attempts with different forged prefixes and the same
real address, and expects `401, 401, 401, 429`.

### A2 — Cacheable financial responses (fixed)

Only the callback page set `Cache-Control`. A `GET /api/transactions` response
carried no cache directive at all, which leaves the decision to the browser's
heuristic caching. Every `/api/` response now carries `Cache-Control: no-store`.

### A3 — Policy gaps (fixed)

The shell's CSP now also sets `form-action 'self'`; script, style, connect,
object, base and frame directives were already locked down, and the bank
callback page keeps its own stricter policy with one hashed inline script.

### A4, A5 — Key derivation strength

Argon2id is configured with 19 MiB, `t=2`, `p=1`, 32-byte output: exactly the
OWASP minimum and a deliberate Phase 0 choice measured on a laptop. A Raspberry
Pi 4/5 has the memory to spend more (64 MiB and `t=3` cost a fraction of a second
there). Two things to know before changing it:

- the parameters live in the vault header, and `rewrapVaultHeader` copies them,
  so an existing vault keeps its parameters even after a passphrase change;
- raising `DEFAULT_KDF_PARAMS` therefore only affects **new** vaults, and
  upgrading an existing one needs a deliberate re-wrap migration, which does not
  exist yet.

### A6 — SQLCipher binding

`@journeyapps/sqlcipher@6.0.0` is a community binding over SQLCipher 4. It is
pinned, its license is in the inventory, and the runtime `cipher_version` is
reported. Keep watching upstream releases; the `record-encryption` engine is the
documented fallback if the binding stops building.

### A7 — The plain-text export

The "every table" ZIP is unencrypted on purpose and includes `banking.json`:
links (authorization and session ids), accounts, provider payloads. Only the
private key is redacted. The archive that carries the connector intact is the
password-encrypted one, and both the UI and `docs/security/privacy.md` say so.

### A8 — The callback route

`GET /enablebanking/auth_callback` runs outside the session and CSRF guard, by
design (ADR 0020): the single-use `state` is the credential, it only completes a
pending link inside an unlocked vault, and a wrong state costs one lookup and
never reaches Enable Banking. It is not rate-limited; on a private network the
worst case is a cheap loop, and the alternative — requiring a session — is what
broke the redirect in the first place.

### A9 — Network exposure

The Compose stack publishes one port, on the interfaces `FLOWLY_BIND_IP` selects.
Flowly never asks the router for a mapping (no UPnP, no NAT-PMP), so internet
reachability can only come from a forward configured elsewhere. On the machine
this was audited on, `upnpc -l` listed five mappings created by another device
on the LAN and none toward this host. `docs/DEPLOYMENT.md` now tells operators to
check the router's forwarding table and to prefer `tailscale serve` when only
the tailnet should reach Flowly.

### A10 — Local key copy

`secrets/<app-id>.pem` is the file downloaded when registering the Enable
Banking application; it is git-ignored, never committed and not needed at
runtime, because the key lives inside the encrypted vault. Delete it once the
application is registered (or keep it in a password manager).

## What holds up

- **Vault at rest.** Argon2id derives the KEK; the DEK is wrapped with
  AES-256-GCM under the vault id as AAD; record subkeys come from HKDF; the DEK
  and KEKs are zeroized on lock. SQLCipher opens with the raw 32-byte key,
  `cipher_memory_security = ON`, WAL and `foreign_keys = ON`. The
  `no-plaintext` suite asserts that a locked vault has no readable records.
- **Sessions.** 32-byte random ids, `HttpOnly`, `SameSite=Strict`, `Secure`
  behind TLS, sliding idle plus absolute expiry, `lock-all` revocation,
  per-session CSRF compared without early exit, origin allow-list, and an
  auto-lock when the last session ends.
- **Imports.** Archives are checksum-verified per entry, extraction rejects
  names with separators or `..` (no zip-slip), entries must be regular files,
  and every import replaces atomically with a snapshot taken first.
- **Provider boundary.** RS256 JWTs with `kid` = application id and a one-hour
  lifetime capped at 24 h, a fixed API origin (no user-controlled base URL, so
  no SSRF), and redirect URLs validated against the application's registered
  list before they are stored.
- **Client.** No third-party script, font or tracker; no `innerHTML`; the CSP
  forbids inline script (except the hashed one on the callback page); the user's
  notes and tags are never overwritten by provider data.
- **Supply chain.** SBOM and license inventory are generated in CI and must
  match the tree; the container runs as the non-root `node` user with
  `no-new-privileges`; the build context excludes the vault, the secrets folder
  and `.env`.

## Residual risks (unchanged, documented)

- An unlocked vault is readable by anyone with access to that browser session
  until it expires or is locked; a compromised client or a keylogger is out of
  scope.
- A host-level attacker with root can read process memory while the vault is
  unlocked.
- Provider data is only as trustworthy as the ASPSP that sends it.
- No independent cryptographic review and no assistive-technology audit yet.
